# Deploy treadmill — stop spending Vercel quota when nothing is published

Date: 2026-09-28 00:05 +06:00
Commit: `13e2078` on `origin/main`

## The problem, measured

Publishing nothing still cost a full Vercel deployment. On 2026-09-27:

```
GitHub deploy.yml runs (UTC day)   42
actual Vercel deployments created  42   <-- 1:1, the guard never fired
by state: {"READY":40,"ERROR":2}
```

Hobby allows 100/day. At that rate the quota is gone by early evening, and
per the note already in `deploy.yml`, once the counter is hit **every** deploy
fails for the rest of the 24h window. This was the exact quota cliff the
2026-09-25 comment in that file was written to prevent, and it had returned.

The dispatcher was **not** the user. `heartbeat.yml` is a self-perpetuating
orchestrator: it runs 5 cycles of images -> pipeline -> auto-author -> deploy
on a 30-min cadence, then `dispatch heartbeat.yml` to restart itself. Of 38
dispatches that UTC day, **27 were `github-actions[bot]`** and 11 were
`manoftec-ai`.

## Why the existing guard did not help

`deploy.yml` already had the right idea: diff reader-visible `SITE_PATHS`
between the live Vercel commit and HEAD, skip if identical. It was correct, and
it was comparing the wrong thing.

`SITE_PATHS` began with `site/src`, and `site/src/data/event-graph.json` is
regenerated by every pipeline cycle. Change rate over a 12h window:

| path | commits |
|---|---|
| `site/src/data` | **29** |
| `site/src/content` | 13 |
| `site/src/pages` | 8 |
| `site/src/components` | 2 |
| `site/src/lib` | 1 |

So the guard saw a diff on essentially every dispatch and deployed every time.

## The fix — two independent layers, neither depends on the other

**1. `deploy.yml` — narrow what counts as reader-visible.**

`SITE_PATHS` now names the paths a reader can actually see and omits
`site/src/data`:

```
site/src/content site/src/pages site/src/components site/src/layouts
site/src/lib site/src/config site/src/content.config.js site/src/styles.css
site/public site/api site/package.json site/astro.config.mjs
```

Generated data now rides along with the next content deploy rather than
triggering one. To stop the event graph going stale, `FORCE_DEPLOY` makes the
**hourly schedule bypass the guard entirely**:

```yaml
FORCE_DEPLOY: ${{ github.event_name == 'schedule' }}
```

So there is still a guaranteed data-only refresh every hour.

**2. `heartbeat.yml` — decide before spending anything.**

It now snapshots `origin/main` before dispatching auto-author, re-reads it
after, and dispatches `deploy.yml` only if a reader-visible path moved. This
saves the Actions minutes too, not just the Vercel deployment.

## Verified against real history, not by inspection

Of the last 60 commits, `c3b492b`, `97965c8` and `625eaa1` are data-only
windows. Old guard: deploys on all three. New guard: skips all three.

Replaying the heartbeat decision over the same commits:

```
7defafb memory: record the enrichment-budget    SKIP (only generated data)
66fb05b homepage audit: lead card ISO date       DISPATCH deploy.yml
0338634 homepage audit: four badges              DISPATCH deploy.yml
ed1c5f7 auto-author: publish drafted stories     DISPATCH deploy.yml
6f37985 memory: audit Vercel storage             SKIP (only generated data)
same sha                                         SKIP (main did not move)
```

## Ceiling

Was ~38 deploys/day of pure churn. Now at most **24/day** scheduled plus one
per genuine content change — with 100/day available, that is real headroom
instead of a race.

## Correction to an earlier note

`site/src/data/event-graph.json` is now **2.9 MB**, not the 54 MB recorded in
`2026-09-27-vercel-storage-gha-audit.md`. It was shrunk after that measurement,
so the deployment-storage and build-time cost from that log is largely gone.
Re-measure before relying on the old figure.
